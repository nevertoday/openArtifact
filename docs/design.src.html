Open Artifact 设计

状态 第一版功能已在本地实现，待部署 日期 2026-10-20 依据 2026-10-20 设计讨论中确认的 15 项决策

任何 AI agent 都能发布 artifact，团队成员不需要 Claude 账号就能查看、评论和使用。整个平台部署在团队自己的 Cloudflare 账号里。

01结论

Open Artifact 是一个与 model 无关的 artifact 平台，面向 Team。第一版的形态如下：

  • 接入：HTTP API 是基础；远程 MCP server 是 agent 的主入口；不支持 MCP 的 agent 使用指南包加 HTTP API。agent 用个人 API token（PAT）鉴权。
  • 能力：静态单页、多文件资源、版本历史、评论、共享数据存储。平台不编译源码。
  • 安全：artifact 在独立 origin 的沙箱 iframe 里运行；页面代码通过 postMessage 代理读写数据，拿不到任何凭证。
  • 部署：Cloudflare Workers + D1 + R2。自托管是指部署到团队自己的 Cloudflare 账号。
  • 开源：Apache-2.0。先在自己团队内部使用 2 到 4 周，达到成功标准后开源，官方 SaaS 最后做。

02问题与目标

Claude Artifact 在两端都绑定 Claude：

生产端

只有 Claude 能创建和发布 artifact。GPT、Gemini、Codex、Cursor 等 agent 没有一个共同的地方可以发布页面。

消费端

查看、评论、使用 artifact 依赖 claude.ai 账号和 Anthropic 的分享权限。

Open Artifact 两端都解决，并且以团队协作为中心设计：发布出来的页面默认整个 workspace 可见，评论能回到 agent 手里，页面能存放团队共享的数据。

不做什么

  • 平台不运行 agent，也不持有任何 LLM key。修改 artifact 的永远是用户自己的 agent。
  • 平台不编译 React / JSX / Markdown 源码。model 自己产出能直接运行的 HTML。
  • 第一版不支持纯内网或离线部署（原因见 部署与开源）。

03系统架构

所有组件都在团队自己的 Cloudflare 账号里。三个 Worker 各管一件事：MCP Worker 把 MCP 调用转成 HTTP API 调用；App Worker 负责主站页面、API、登录和权限；Usercontent Worker 只在独立 origin 上提供 artifact 文件。

组件职责不做
App Worker查看页 UI、HTTP API、Better Auth 登录、PAT 校验、权限检查、postMessage 代理、触发截图和邮件不提供 artifact 文件本身
MCP Worker远程 MCP server，工具定义和使用说明；每个工具调用经 service binding 转成一次 HTTP API 调用，带着 agent 的 PAT 和客户端名没有自己的业务逻辑和存储
Usercontent Worker在 *.usercontent 域上只读提供 artifact 文件，只接受 app 签名的路径；给每个页面注入共享数据 SDK；通过 app 的 RPC 入口 ArtifactFileReader 读取文件不读 cookie，不接受写请求，没有 D1 和 R2 绑定
D1用户、workspace、成员、artifact 元数据和版本号、评论、共享数据（JSON 列）、PAT hash不存文件
R2每个版本的文件、缩略图不存元数据
Browser Rendering发布时为链接预览截一张缩略图
邮件发送magic link 登录邮件、评论通知（Resend 或 Cloudflare Email，待选）

04接入层

“不同 model 都能用”的体验，取决于 model 能不能知道这个平台怎么用。只提供 API 不够：model 不知道什么时候该发布、页面该遵守什么约定、该更新而不是新建。所以接入层由三部分组成。

入口给谁用说明从哪来版本
远程 MCP serverClaude Code、Codex、Cursor、Gemini CLI 等支持 MCP 的 agent工具描述自动进入 agent 上下文；get_guide 按需返回页面规范第一版
HTTP API脚本、CI、不支持 MCP 的 agentOpenAPI 规范 + /llms.txt第一版
指南包所有 agent一份源文件生成 AGENTS.md 片段、Claude Skill、Cursor rules；设置页一键复制，已填好本实例的 API 地址第一版
CLI能执行 shell 的 agent、人HTTP API 的薄封装以后
Chat 网页内接入ChatGPT、Gemini 网页版用户每个平台单独适配不做

MCP 工具

MCP Worker 第一版提供下面的工具。每个工具对应一个 HTTP API 端点，权限和发 token 的用户相同。

工具作用
publish新建 artifact，上传页面和资源文件，返回 url 和 version
update基于 baseVersion 发布新版本；版本不一致时被拒绝（见 版本与并发）
read读取当前版本的文件和 version
list列出当前用户在 workspace 里能看到的 artifact
list_comments读取评论，可以只取标记为“给 agent”且未解决的评论
reply_comment回复一条评论，可以同时标记为已解决
get_guide返回页面规范：标题、主题、CDN 白名单、什么时候更新而不是新建

PAT

  • 用户在设置页生成 PAT。平台只存 hash，明文只在生成时显示一次。
  • 每个 PAT 只对一个 workspace 有效，可以设过期时间，可以随时撤销。
  • agent 的权限等于发 PAT 的用户在该 workspace 里的权限，平台没有单独的 agent 角色。

版本与并发

团队里多个人的 agent 可能同时修改同一个 artifact。平台用乐观锁处理：每次 read 返回 version，update 必须带上 baseVersion。

  1. App API 只在当前版本等于 baseVersion 时写入新版本。
  2. 版本不一致时，App API 拒绝写入，并在响应里返回最新内容和差异。
  3. agent 把自己的修改合并到最新内容上，再次调用 update。
  4. 只有用户明确要求覆盖时，agent 才可以传 force: true。

存储层（M1 已实现）保证失败或落败的发布不会留下没有文件的版本：

  1. 先把文件写到 R2 的一个新上传目录 artifacts/{artifactId}/uploads/{uploadId}/。
  2. 用一个 D1 batch（事务）更新 artifacts：只有 current_version 仍然等于 baseVersion 时，才把版本号加一，并把 current_upload_id 指向这次上传。
  3. 同一个 batch 里，版本记录和文件清单只在 current_upload_id 已经指向这次上传时才写入。
  4. 版本号没有更新成功时，删除这次上传的文件，并返回 conflict（带当前版本号）或 not_found。
packages/storage-cloudflare/src/cloudflare-artifact-repository.ts · 50–64逐字摘录
  async publishOnTopOf(artifactId: string, baseVersion: number, authorId: string, files: ArtifactFile[]): Promise<PublishResult> {
    const nextVersion = baseVersion + 1
    const publishedAt = Date.now()
    const { batchResults, uploadId } = await this.#writeVersion(artifactId, files, uploadId => [
      this.#db
        .prepare('UPDATE artifacts SET current_version = ?, current_upload_id = ?, updated_at = ? WHERE id = ? AND current_version = ?')
        .bind(nextVersion, uploadId, publishedAt, artifactId, baseVersion),
      ...this.#recordVersionStatements(artifactId, nextVersion, uploadId, authorId, files, publishedAt),
    ])
    const versionAdvance = batchResults[0]
    const claimedNextVersion = versionAdvance?.meta.changes === 1
    if (claimedNextVersion) return { status: 'published', version: nextVersion }
    await this.#discardUpload(artifactId, uploadId, files)
    return this.#rejectionFor(artifactId)
  }

冲突时返回最新内容和差异，是 App API（任务 15）的工作，存储层只返回当前版本号。

06协作闭环

典型流程：作者让 agent 发布一份设计文档，同事在页面上评论，作者让 agent 去处理评论，agent 修改后重新发布并回复评论。agent 不是常驻的，所以第一版靠作者叫 agent 来拉取评论。

评论的两种用途

评论分两种：人与人的讨论，以及给 agent 的修改意见。评论者把评论标记为“给 agent”后，list_comments 可以只取这类未解决的评论，agent 不会被讨论内容干扰。agent 修改后回复这条评论并标记为已解决，其他人在页面上能看到处理结果。

人收到的通知

  • 链接预览：查看页带完整的 Open Graph 元数据和发布时截的缩略图，贴到 Slack、飞书、钉钉时显示卡片。
  • 邮件：有人评论你的 artifact、@你、回复你的评论时，平台发邮件。邮件通道和 magic link 登录共用。

第一版

  • MCP 拉取评论
  • “给 agent”标记
  • 回复并解决
  • OG 预览、邮件

第二版

  • Webhook：新评论、新版本事件
  • Slack / 飞书 bot（基于 Webhook）

不做

  • 平台收到 @agent 后自己调 model 修改

07沙箱与共享数据

artifact 是 model 生成的任意代码。如果 artifact 和主站同 origin，一个恶意或有缺陷的页面就能读取查看者的登录态。所以 artifact 必须由 Usercontent Worker 在独立 origin 上提供，并且放在 sandbox iframe 里运行。这是安全底线，自托管也不能省。

独立 origin 带来一个问题：页面代码拿不到主站的 cookie，也就无法直接调用数据 API。解决方法是 postMessage 代理：页面代码通过平台注入的 SDK 发消息给父页面，由查看页代为调用 API。

artifact 页面代码使用共享数据示例，SDK 接口尚未定稿

  // The platform stamps createdBy with the viewer; the page never sends an identity.

  renderSignups(await signupSheet.list())

谁能读写

访问者读写
能看到这个 artifact 的 workspace 成员可以可以
公开链接访客（匿名）可以默认不可以。作者为这个 artifact 单独开启匿名写入后才可以，并且有限流
  • 每条记录自动带上 createdBy 和 updatedBy。页面能拿到当前查看者的名字和头像。
  • 只有在查看页里打开时，页面才能写数据。直接打开 usercontent 地址时，页面没有父页面代理，数据功能不可用。
  • 查看页收到消息后，必须先确认 event.origin 是 usercontent 域，并且 event.source 是它自己创建的那个 iframe，才处理消息。

08账号与权限

组织层级

第一版用扁平结构：用户 → Workspace → artifact。一个用户可以加入多个 workspace。以后需要时可以在 workspace 上面加 Organization，现有数据不用迁移。

artifact 的可见范围

范围谁能看说明
私有作者本人
指定的人作者指定的成员角色分 viewer、commenter、editor
Workspace 内workspace 全部成员默认值。发布出来就是给同事看的
公开链接任何拿到链接的人，不需要登录可以设过期时间和密码。workspace 管理员可以全局关闭

登录

认证用 Better Auth，数据存在 D1。用户数据始终留在部署者自己的 D1 里，自托管实例和官方 SaaS 用同一套代码。

  • GitHub / Google OAuth
  • 邮箱 magic link
  • 可配置的通用 OIDC，用于接入公司 SSO（Okta、Azure AD、飞书、钉钉等）

团队可以在实例前面再加一层 Cloudflare Access。这是团队的可选项，平台不依赖它。

09部署与开源

自托管 = 部署到自己的 Cloudflare 账号

Workers、D1、R2 是 Cloudflare 的托管服务，不能用 docker 在内网运行。所以本项目的“自托管”是指：团队用仓库里的 “Deploy to Cloudflare” 按钮或 wrangler deploy，把整套服务部署到团队自己的 Cloudflare 账号。数据存在团队自己的 D1 和 R2 里，不经过项目方的服务器。官方 SaaS 是同一套代码部署在项目方的账号上。

代价：需要纯内网或离线部署的团队，第一版无法使用。

为以后的 Postgres 适配留余地

业务代码必须通过 repository 层访问数据，不直接调用 D1 或 R2 的 API。这样以后社区要加 Postgres + S3 适配时，只替换 repository 的实现。

两个域名

部署者要配置两个域名，或者一个域名加一个子域：主站给 App Worker 和 MCP Worker，*.usercontent 给 Usercontent Worker。部署文档必须写清楚这一点和原因（见 沙箱与共享数据）。

许可证

Apache-2.0。它和 MIT 一样宽松，另外包含专利授权条款，企业法务更容易接受。宽松许可证意味着任何人都可以用这套代码做竞争的托管服务，这一点在讨论时已经接受。

未核实Cloudflare 的远程 MCP 方案（agents SDK 的 McpAgent）、Browser Rendering 的额度和价格，本文没有核实。实现前要确认。

11第一版任务

第一版分 9 个阶段（M0 到 M8），按依赖顺序排列。M0 的结论会影响 M2 及之后的实现方式，所以 M2 开始前必须完成 M0；M1 不依赖 M0 的结论，可以和 M0 同时开始。M2 完成后，M3 到 M6 可以部分并行。任务编号全文连续，阶段旁边的“依赖”指的是任务编号。

M0 技术验证→骨架 7–9→权限服务 13→发布 API 14–15→MCP Worker 22→评论闭环 26–27→Dogfood

共享数据（M6）和通知（28–29）不在关键路径上，可以和评论闭环并行做。

M0 技术验证

无依赖
  1. Better Auth on Workers + D1：GitHub OAuth、magic link、一个 OIDC 提供方都能登录成功。
  2. 远程 MCP + PAT：用 McpAgent 写一个最小工具，Claude Code、Codex、Cursor 三种客户端都能带 PAT 调通。
  3. 两个域名 + 沙箱：Usercontent Worker 从 R2 提供页面，主站用 sandbox iframe 嵌入；验证 iframe 里读不到主站 cookie。
  4. Browser Rendering：能对 usercontent 页面截缩略图；确认额度和价格。
  5. 选邮件服务：比较 Resend 和 Cloudflare Email 的发信能力和自托管配置成本，选定一个。
  6. 定数值：单个 artifact 和单个文件的大小上限、CDN 白名单。

M1 骨架

已完成无依赖，可以和 M0 同时开始
  1. Monorepo：TS + pnpm；三个 Worker（app / mcp / usercontent）各有 wrangler 配置；CI 跑类型检查和测试。
  2. 数据模型和 D1 migration：users（实际改由 Better Auth 创建，见 实施进展）、workspaces、memberships、artifacts、artifact_versions、artifact_grants、comments、shared_documents、personal_access_tokens。
  3. Repository 层：业务代码只依赖 repository 接口；业务代码里搜不到直接调用 D1 或 R2 的地方。

M2 账号与权限

依赖 1、8、9
  1. 登录：接入 Better Auth；OAuth、magic link、OIDC 可以配置。
  2. Workspace：能创建 workspace、邀请成员；角色分 admin 和 member；一个用户可以加入多个 workspace。
  3. PAT：生成时明文只显示一次；只存 hash；有过期时间；可以撤销；只对一个 workspace 有效。
  4. 权限服务：支持四种可见范围、viewer / commenter / editor 三种角色、管理员全局关闭公开链接。API、查看页、数据代理都只通过这个服务判断权限。

M3 发布与查看

依赖 9、13
  1. API：publish / read / list：每个版本的文件存 R2，元数据存 D1。
  2. API：update：带乐观锁（baseVersion）和 force；冲突时返回最新内容和差异。写 R2 失败时，D1 里不能留下没有文件的版本（见 版本与并发）。
  3. 版本历史：能列出版本、对比两个版本、回滚。回滚是把旧版本作为新版本发布，共享数据不变。
  4. Usercontent Worker：只读提供文件；按 CDN 白名单设置 CSP；不读 cookie；拒绝写请求。
  5. 查看页：sandbox iframe、版本切换、分享设置。
  6. 公开链接：支持过期时间和密码。
  7. 大小上限：API 按第 6 项定的数值拒绝超限的请求。
  8. OpenAPI 规范和 /llms.txt

M4 接入层

依赖 2、14、15
  1. MCP Worker：publish、update、read、list、get_guide，每个工具转成一次 HTTP API 调用。
  2. 指南源文件：写明页面约定（标题、主题、CDN 白名单）、什么时候更新而不是新建、冲突后怎么合并。
  3. 指南包生成：由第 23 项生成 AGENTS.md 片段、Claude Skill、Cursor rules；设置页一键复制，自动填好本实例的 API 地址。
  4. 记录发布来源：每次发布记下 MCP 客户端名或 User-Agent。dogfood 阶段靠它统计用了几种 agent。

M5 评论与通知

依赖 13、18；第 28 项还依赖 5；第 29 项还依赖 4
  1. 评论：API 和查看页 UI，支持回复、@成员、标记“给 agent”、标记已解决。
  2. MCP 工具：list_comments 可以只取“给 agent”且未解决的评论；reply_comment 回复时可以同时标记已解决。
  3. 邮件通知：有人评论你的 artifact、@你、回复你的评论时，你收到邮件。
  4. 链接预览：查看页带 OG 元数据；发布时截缩略图存到 R2。

M6 共享数据

依赖 3、13、17、18
  1. 数据 API：按 collection 存文档；每条记录自动带 createdBy 和 updatedBy；能返回当前查看者的名字和头像。
  2. SDK：Usercontent Worker 给页面注入 window.openArtifact.db；接口定稿后写进第 23 项的指南。
  3. postMessage 代理：查看页先校验 event.origin 和 event.source，再代为调用数据 API；用 requestId 把结果对应回原请求。
  4. 匿名写入：默认关闭；作者可以为单个 artifact 开启；开启后有限流。

页面

设计稿里的 5 个页面都已实现：首页（带实时缩略预览）、查看页（评论 / 版本 / 数据三个标签，评论可以锚定到页面上的位置，页面里显示编号标记）、分享对话框、设置（Agent 接入、个人资料、成员、Workspace 设置）、登录页。另外加了公开链接的密码页。

和设计不同的地方

  • 注册有白名单。登录就会加入团队 workspace，所以开放注册等于把内容交给任何人。部署时用 ALLOWED_EMAIL_DOMAINS 设置允许的邮箱域名；不设置时，只有第一个人（创建者）能注册。
  • usercontent 用签名地址提供文件。usercontent 不读 cookie，所以查看页给每个查看者签发一个 6 小时有效的版本路径前缀；页面里的相对链接沿用这个前缀。
  • usercontent 没有存储权限。它通过 app 的 RPC 入口 ArtifactFileReader（只能经 service binding 调用）读取文件，自己没有 D1 和 R2 绑定。
  • 沙箱靠两层：iframe 的 sandbox 属性，加上 usercontent 响应头里的 CSP sandbox 指令，所以在新标签页单独打开也有隔离。
  • postMessage 的来源校验改为检查窗口。沙箱页面的 origin 是 null，查看页改为确认消息来自自己创建的 iframe 窗口；SDK 只把消息发给 app 的 origin，代理只接受安全的集合名和文档 id。
  • 评论只有一层回复。回复一条回复时，它挂到所在讨论串的第一条评论下。
  • PAT 只在创建它的 workspace 里生效，即使它的主人也在别的 workspace。
  • 公开链接的密码尝试有限流：每个访客地址每个 artifact 每分钟 10 次。
  • 没有配置邮件服务时，发送登录邮件直接报错，不会把登录链接写进生产日志。本地开发用 MAILER=console。
  • 界面字体用系统中文字体，不依赖 Google Fonts，在国内网络下也能直接显示。

  • pnpm run check 全部通过：存储边界检查、5 个包的类型检查、100 个测试。测试在 Workers 运行时里对本地 D1 和 R2 运行，登录走真实的 Better Auth 邮箱链接流程。
  • 独立代码评审找到 2 个严重问题（任何人登录都能加入团队、next 参数可以借制表符跳转到外站）和 6 个重要问题，都已修复，每个都有回归测试。
  • 本地端到端：用 MCP 以 Claude Code 身份连接，发布带共享数据的报名页；同事留“给 agent”的评论；agent 读评论、更新、遇到过期版本时收到合并提示、回复并解决。全部成功。
  • 浏览器（Chrome）实测：沙箱页面里的 SDK 以当前查看者身份读写数据，页面拿不到 cookie 和 localStorage；分享对话框设置公开链接和密码；匿名访客输入密码后能用页面但不能评论；设置页创建 token。1440px、390px 和深色模式下截图检查，页面不横向滚动，控制台没有错误。

13待决定的事

第 2、3、4 项在 M0 技术验证时决定（任务 5、6）。

  1. MIT 还是 Apache-2.0
    讨论时选了宽松许可证，本文默认 Apache-2.0（多了专利授权）。建议保持 Apache-2.0。
  2. 单个 artifact 和单个文件的大小上限
    讨论中没有定。建议参考 D1 和 R2 的限制，在技术验证时定数值。
  3. CDN 白名单
    讨论中没有定。建议第一版沿用 cdnjs、jsDelivr、unpkg，并允许 workspace 管理员增加。
  4. 邮件服务用 Resend 还是 Cloudflare Email
    建议在技术验证时比较发信能力和自托管配置成本后再选。
  5. SaaS 上公开内容的滥用治理
    只影响官方 SaaS，建议在 SaaS 阶段再定。
  6. 共享数据 SDK 的接口
    本文示例中的 window.openArtifact.db 只是示意。建议在实现时和指南包一起定稿。
